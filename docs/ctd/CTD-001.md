# CYCLONE

Enterprise Technical Directive · CTD-001 · Version 1.0

Loop Current Detector, Compiler & Adaptive Execution Runtime

Architecture directive

Rust-first · Tov-native · Evidence-gated · Agent-agnostic

## 1. Executive mandate

Cyclone SHALL be developed as an autonomous behavioural compilation system capable of observing agent workflows, detecting repeatable non-generative computational activity, converting suitable activity into reusable executable currents, and composing those currents into synchronised execution graphs known as cyclones.

Its primary objective is to reduce unnecessary inference, orchestration overhead, tool-selection latency and duplicated computation without compromising execution correctness, environmental awareness, security or agent autonomy.

Foundational principle:

> An agent should not repeatedly reason through a computational process that has already been sufficiently understood, verified and compiled.

Cyclone SHALL NOT replace generative reasoning indiscriminately. It SHALL identify the computational boundary between work requiring intelligence and work that can be executed reliably without fresh inference.

### 1.1 Mandatory outcomes

1. Discover recurrent action patterns from live and historical agent execution traces.
2. Classify observed action sequences into high-pressure, low-pressure and gust currents.
3. Compile eligible currents into portable, versioned executable representations.
4. Compose currents into dependency-aware cyclones with parent-child synchronisation.
5. Continuously validate compiled behaviour against observed execution semantics.
6. Detect environmental drift and automatically demote, suspend or invalidate affected currents.
7. Provide auditable provenance for every classification, compilation and execution.
8. Support multi-agent and multi-repository current reuse with strict isolation.
9. Demonstrate measurable net improvements in latency, inference consumption and computational expenditure.
10. Preserve deterministic fallback to the original agent workflow wherever technically possible.

## 2. Fundamental ontology

Cyclone SHALL distinguish the following entities.

| Entity              | Definition                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------------- |
| Observation         | Captured evidence of an agent or tool action                                                |
| Trace               | Ordered or causally linked observations from an execution                                   |
| Segment             | Candidate bounded sequence of non-generative actions                                        |
| Current             | Reusable computational pattern derived from one or more segments                            |
| Pressure            | Evidence-based classification of a current's repeatability and computational predictability |
| Cyclone             | Composed graph of currents and their execution relationships                                |
| Synchronousity      | Binding of a child current's activation or progression to parent activity                   |
| Compilation         | Transformation of a validated current into an executable representation                     |
| Gust                | Non-repeatable, insufficiently understood or economically unsuitable action pattern         |
| Pressure transition | Evidence-driven promotion or demotion of a current                                          |
| Drift               | Material deviation from the assumptions supporting a compiled current                       |

A current SHALL be defined by behaviour, input and output contracts, side-effect semantics and environmental dependencies—not by textual similarity between agent prompts.

### 2.1 Current classification

High pressure — HP

A computationally stable current with sufficiently repeatable execution structure and verified deterministic or explicitly bounded output behaviour.

Target: statically compiled or directly executable procedure with minimal runtime planning.

Low pressure — LP

A repeatable structural pattern whose variable space is bounded, computationally manageable and expressible through typed parameters or guarded branches.

Target: parameterised executable procedure, potentially synchronised with a parent HP current.

Gust — G

An irregular, low-value, insufficiently evidenced or unsuitable pattern.

Target: observation, agent execution, or retirement. Gusts are not automatically compilation failures.

Classification SHALL be dynamic. No current shall be permanently designated high pressure solely because its historical execution was stable.

## 3. Reference system architecture

The architecture SHALL comprise six primary subsystems.

### 3.1 Observation subsystem

The observer SHALL capture non-generative activity through instrumented tool adapters, agent runtime hooks and compatible trace collectors.

Minimum observation fields:

```
pub struct ActionObservation {
    pub observation_id: ObservationId,
    pub trace_id: TraceId,
    pub parent_span_id: Option<SpanId>,
    pub agent_id: AgentId,
    pub tenant_id: TenantId,
    pub action_kind: ActionKind,
    pub input_digest: Digest,
    pub output_digest: Digest,
    pub environment_digest: Digest,
    pub started_at: Timestamp,
    pub completed_at: Timestamp,
    pub effect_class: EffectClass,
    pub outcome: ActionOutcome,
    pub evidence_refs: Vec<EvidenceRef>,
}
```

The observer MUST preserve causal ordering, even when multiple agents or tools execute concurrently.

It SHALL NOT infer ordering solely from wall-clock timestamps.

Sensitive arguments, credentials, personal data and unredacted tool responses SHALL NOT be recorded by default. Where detailed payload capture is necessary, it SHALL require explicit authorisation and retention controls.

### 3.2 Segmentation subsystem

The detector SHALL identify candidate currents through structural sequence analysis.

Candidate detection methods SHOULD include:

- Repeated subsequence mining.
- Canonical action signature matching.
- Causal graph motif detection.
- Parameter variance analysis.
- Branch stability analysis.
- Side-effect equivalence analysis.
- Cross-trace and cross-agent pattern discovery.

Segmentation SHALL respect transactional boundaries and externally visible side effects.

A sequence containing a model call MAY be partitioned into non-generative subcurrents, but Cyclone SHALL NOT silently compile the model's semantic decision into a fixed action.

### 3.3 Pressure classification subsystem

Pressure classification SHALL be evidence-based and multidimensional.

Define the initial pressure evidence vector:

\[ \mathbf{P}(c)=(R,D,V,S,B,E) \]

Where:

| Signal  | Meaning                                      |
| ------- | -------------------------------------------- |
| \(R\) | Structural recurrence                        |
| \(D\) | Determinism or bounded output predictability |
| \(V\) | Validation confidence                        |
| \(S\) | Environmental stability                      |
| \(B\) | Parameter-space boundedness                  |
| \(E\) | Expected economic benefit                    |

The classifier SHALL use configurable policy gates rather than rely exclusively on a weighted average.

Initial suggested eligibility gates, subject to empirical calibration:

| Condition                           | High pressure                 | Low pressure                  |
| ----------------------------------- | ----------------------------- | ----------------------------- |
| Independent successful observations | ≥30                           | ≥15                           |
| Structural agreement                | ≥99%                          | ≥90%                          |
| Replay equivalence                  | 100% on required safety tests | 100% on required safety tests |
| Parameter variation                 | Minimal or fixed              | Bounded and typed             |
| Net expected benefit                | Positive                      | Positive                      |
| Unknown side effects                | Prohibited                    | Prohibited                    |

These numbers are provisional engineering targets, not statistically sufficient proof of correctness.

Rare, high-impact branches SHALL require targeted testing regardless of aggregate success rates.

### 3.4 Compilation subsystem

Cyclone SHALL compile current definitions into a typed intermediate representation (CIR).

CIR SHALL encode:

- Input and output types.
- Preconditions and postconditions.
- Action dependencies.
- Environmental constraints.
- Side-effect declarations.
- Retry and idempotency policies.
- Scheduling semantics.
- Fallback targets.
- Versioned validation evidence.

The initial compiler SHOULD target an interpreted or ahead-of-time optimised CIR runtime rather than immediately generating native machine code.

Native compilation, WASM and specialised execution backends MAY be introduced once measured workload characteristics justify them.

Compilation SHALL NOT be considered successful merely because executable code was produced. Semantic equivalence and policy compliance are mandatory release gates.

## 4. Cyclone composition and synchronousity

A cyclone SHALL be represented as a typed directed execution graph:

\[ C=(N,E,T,G) \]

Where \(N\) denotes current instances, \(E\) causal dependencies, \(T\) timing and activation constraints, and \(G\) runtime guards.

The compiler SHALL support four relationships.

| Relationship      | Behaviour                                                     |
| ----------------- | ------------------------------------------------------------- |
| Sequential        | Child begins after parent completion                          |
| Event-synchronous | Child activates on a specified parent event                   |
| Phase-synchronous | Child advances according to parent execution milestones       |
| Data-synchronous  | Child activates when required parent outputs become available |

Low-pressure currents SHALL be permitted to inherit parent timing, context and parameter values.

However, synchronisation SHALL NOT imply that child and parent must occupy the same execution thread.

### 4.1 Parent-child contract

```
pub struct SyncContract {
    pub parent: CurrentId,
    pub child: CurrentId,
    pub trigger: SyncTrigger,
    pub input_bindings: Vec<InputBinding>,
    pub deadline: Option<Duration>,
    pub cancellation: CancellationPolicy,
    pub failure: FailurePolicy,
}
```

The runtime MUST enforce:

1. No child execution before its trigger conditions are satisfied.
2. No unbounded dependency cycles.
3. No propagation of unvalidated parent outputs into privileged child actions.
4. Explicit cancellation and timeout semantics.
5. Deterministic resolution of conflicting activation events.

Loops MAY exist as explicit bounded or termination-proven control-flow constructs, but not as uncontrolled scheduling cycles.

## 5. Current optimisation

Cyclone SHALL perform optimisation at both current and cyclone level.

### 5.1 Current-level optimisation

Permitted transformations include:

- Redundant action elimination.
- Common input normalisation.
- Deterministic branch simplification.
- Reuse of verified pure computations.
- Parameter binding and partial evaluation.
- Elimination of unnecessary tool-discovery operations.
- Safe batching of compatible actions.

### 5.2 Cyclone-level optimisation

The compiler SHOULD detect opportunities for:

- Common-subgraph elimination.
- Shared dependency inspection.
- Concurrent execution of independent currents.
- Intermediate result reuse.
- Critical-path shortening.
- Parent-trigger consolidation.
- Cross-agent resource coordination.

Optimisations SHALL preserve observable semantics, including ordering constraints, permissions, side effects and failure behaviour.

For example, two repository inspections MAY be consolidated if they use the same authorised snapshot and equivalent inspection parameters.

Two payment operations SHALL NOT be consolidated merely because their tool calls look identical.

## 6. Adaptive pressure lifecycle

Current lifecycle state machine

Each current SHALL maintain a lifecycle state independent of its pressure classification.

A high-pressure current may be suspended. A low-pressure current may be active. A gust may remain under observation indefinitely.

Promotion SHALL require evidence of semantic correctness, economic benefit and operational stability.

Demotion or suspension SHALL occur when:

- Required validation fails.
- Environmental assumptions become invalid.
- A dependency version changes incompatibly.
- A security policy changes.
- Side-effect behaviour deviates.
- The compiled implementation becomes economically inferior.
- The original workflow's semantics materially change.

Pressure hysteresis SHOULD prevent frequent promotion and demotion caused by marginal fluctuations.

## 7. Correctness and semantic equivalence

This is Cyclone's highest-priority engineering requirement.

Cyclone SHALL optimise behaviour, not merely reproduce action sequences.

Equivalent inputs do not necessarily justify identical actions when permissions, environmental state or external side effects differ.

Every compiled current SHALL declare its equivalence contract.

### 7.1 Equivalence categories

| Category                   | Verification requirement                                                         |
| -------------------------- | -------------------------------------------------------------------------------- |
| Pure computation           | Exact output equality or explicitly defined numeric tolerance                    |
| Read-only tool workflow    | Equivalent results under a controlled environment snapshot                       |
| Filesystem mutation        | Equivalent resulting state, permissions and expected side effects                |
| External API mutation      | Contract-level equivalence, idempotency and authorised execution                 |
| Time-dependent workflow    | Defined temporal tolerances and expiry conditions                                |
| Non-deterministic workflow | Explicit invariants, bounded outcomes and distributional tests where appropriate |

### 7.2 Verification modes

Cyclone SHALL support:

Shadow mode: Execute the original workflow and a safe compiled candidate against equivalent inputs, comparing outputs and permitted effects. Mutating operations SHALL use isolated fixtures, simulations or other non-production environments.

Canary mode: Route a controlled proportion of eligible production executions through the compiled current with rollback controls.

Active mode: Execute the compiled current as the preferred route, retaining continuous monitoring and fallback.

A compiled current SHALL never be allowed to duplicate irreversible external actions simply to establish equivalence.

## 8. Runtime design

The initial runtime SHALL be implemented in stable Rust.

Recommended components:

| Component           | Responsibility                                  |
| ------------------- | ----------------------------------------------- |
| `cyclone-observe`   | Trace collection and normalisation              |
| `cyclone-detect`    | Pattern discovery and segmentation              |
| `cyclone-pressure`  | Classification and lifecycle decisions          |
| `cyclone-ir`        | Typed current intermediate representation       |
| `cyclone-compile`   | Graph transformations and executable generation |
| `cyclone-runtime`   | Execution, scheduling and cancellation          |
| `cyclone-verify`    | Replay, equivalence and policy validation       |
| `cyclone-registry`  | Artifact versioning and provenance              |
| `cyclone-telemetry` | Performance, drift and economics                |
| `cyclone-tov`       | Tov transport integration                       |

Tov SHALL be the preferred ecosystem transport, subject to a defined wire protocol and interoperability tests.

The runtime SHALL expose an adapter boundary for agents and tools that do not use Tov.

### 8.1 Execution guarantees

Cyclone SHALL implement explicit execution guarantees according to action type.

Pure computations MAY be retried freely within resource limits.

Idempotent operations MAY be retried according to declared policy.

Non-idempotent operations MUST use operation identifiers, durable execution journals and reconciliation where available.

Exactly-once external side effects SHALL NOT be claimed without an underlying transactional mechanism capable of providing that guarantee.

## 9. Security, tenancy and governance

Cyclone SHALL adopt a zero-trust execution model.

The compiler MUST NOT elevate the permissions of an observed workflow.

Every current SHALL execute under an explicit authority context defining tenant, principal, permitted resources and allowed operations.

### 9.1 Mandatory controls

- Tenant-isolated trace storage and current registries.
- Least-privilege tool execution.
- Cryptographically verifiable artifact provenance.
- Signed or otherwise authenticated compilation artifacts.
- Secret redaction and prohibition of credential embedding.
- Resource and execution quotas.
- Audit logs for compilation, promotion, execution and rollback.
- Protection against malicious trace poisoning.
- Protection against prompt-injection-derived tool behaviour being promoted into trusted automation.
- Revocation and emergency disablement of deployed currents.

Cross-tenant current reuse SHALL require a separately validated, tenant-neutral implementation and fresh authorisation under the consuming tenant's permissions.

Historical observation of a privileged action SHALL never constitute permission to execute it again.

## 10. Economics and optimisation objectives

Cyclone SHALL optimise net operational value rather than raw execution speed alone.

For a candidate current \(c\):

\[ V_c = N_c(C_o-C_c) - (C_d+C_v+C_m+C_r) \]

Where:

- \(N_c\): Expected eligible executions over the evaluation horizon.
- \(C_o\): Cost per original execution.
- \(C_c\): Cost per compiled execution.
- \(C_d\): Detection and compilation cost.
- \(C_v\): Validation cost.
- \(C_m\): Expected maintenance and monitoring cost.
- \(C_r\): Expected risk-adjusted failure and recovery cost.

All terms SHALL use consistent monetary units and a defined evaluation horizon.

A current with \(V_c \leq 0\) SHOULD NOT be promoted solely for economic optimisation, although other documented operational objectives may justify it.

Cyclone SHALL track:

Inference

Calls and tokens avoided

Latency

End-to-end and critical path

Compute

CPU, memory and I/O cost

Correctness

Equivalent execution rate

Recovery

Rollback and fallback overhead

Reuse

Cross-workflow adoption

Savings claims SHALL be based on paired workloads with matched input conditions, reported uncertainty and fully accounted compilation and verification overhead.

## 11. Enterprise observability

Cyclone SHALL provide an operator-facing execution and optimisation dashboard.

Minimum required views:

- Current registry: pressure, version, owner, evidence, status and deployment scope.
- Cyclone graph: parent-child dependencies, activation triggers and critical path.
- Pressure history: transitions, confidence and drift causes.
- Compilation report: transformations, validation outcomes and artifact hashes.
- Economic report: avoided inference, net cost and break-even estimates.
- Execution trace: causal action history and fallback events.
- Safety report: rejected promotions, policy violations and suspended currents.

All operational metrics SHOULD be exportable using OpenTelemetry-compatible interfaces.

## 12. Delivery programme

The programme SHALL be delivered through evidence-gated phases rather than feature-count milestones.

Phase 0 — Repository reconnaissance and baseline

Inspect existing ecosystem repositories, Tov interfaces, trace formats, agent execution contracts and validation infrastructure before implementing new abstractions.

Deliver architecture decision records, a workload corpus, threat model and baseline cost measurements.

Phase 1 — Observation and detection

Implement trace ingestion, causal normalisation, segmentation, candidate mining and pressure classification.

Exit only when detected candidates can be reproduced from versioned traces and manually audited.

Phase 2 — Current compiler

Implement CIR, type checking, guarded compilation, deterministic replay and shadow verification.

Exit only when eligible pure and read-only workflows pass equivalence tests.

Phase 3 — Cyclone composition

Implement DAG compilation, synchronousity contracts, scheduling, shared computations and critical-path optimisation.

Exit only when composed currents preserve declared causal and side-effect semantics.

Phase 4 — Adaptive production runtime

Implement canary deployment, drift detection, pressure transitions, rollback, policy enforcement and operational telemetry.

Exit only after fault-injection, isolation, recovery and security acceptance tests.

Phase 5 — Portfolio-wide optimisation

Implement cross-agent pattern discovery, compatible current reuse, registry federation and shared optimisation economics.

Exit only when reuse benefits are demonstrated without tenant leakage or authority escalation.

## 13. Acceptance criteria

The following are proposed release targets. They SHALL be calibrated against Phase 0 baselines and approved workload classes before becoming binding production service-level objectives.

| Metric                               | Initial target                                                         |
| ------------------------------------ | ---------------------------------------------------------------------- |
| Required semantic equivalence tests  | 100% pass                                                              |
| Unauthorised privilege escalation    | Zero tolerated                                                         |
| Undeclared external side effects     | Zero tolerated                                                         |
| Trace causal reconstruction          | 100% on instrumented test corpus                                       |
| Deterministic replay reproducibility | 100% on supported deterministic fixtures                               |
| Compiled execution latency           | ≥25% improvement on qualifying workloads                               |
| Net inference consumption            | ≥30% reduction on selected repetitive workflows                        |
| Automatic invalidation               | All known incompatible dependency changes detected in controlled tests |
| Fallback reliability                 | 100% of tested recoverable failure scenarios                           |
| Audit completeness                   | 100% of promoted artifact and execution decisions attributable         |

No aggregate performance gain SHALL compensate for a failed mandatory safety or correctness gate.

## 14. Adversarial test programme

The verification suite MUST include deliberately hostile and misleading workflow evidence.

Required scenarios include:

1. Identical tool-call sequences producing different results because of hidden environmental state.
2. Repeated workflows containing non-idempotent operations.
3. Prompt-injection-induced repetition that attempts to establish a malicious current.
4. Concurrent parent events activating the same child.
5. Dependency updates between observation and execution.
6. Cross-tenant traces with structurally identical actions but different authority.
7. Partial failure during a multi-current cyclone.
8. Stale cache values that appear equivalent under superficial comparison.
9. Long-running currents with cancellation and timeout races.
10. Rare conditional branches absent from ordinary training traces.
11. Apparent economic gains erased by compilation or monitoring costs.
12. Agent workflows whose action sequences match but whose underlying objectives differ.

The test programme SHALL include property-based testing, fuzzing, differential execution, fault injection and controlled adversarial traces.

## 15. First reference workload

The initial reference workload SHOULD be a repository-analysis workflow with no production mutation privileges.

Reference Cyclone: Repository Preflight

1. Observe repeated repository inspection and metadata collection.
2. Detect stable filesystem and manifest inspection sequences.
3. Classify repository identification as a candidate high-pressure current.
4. Classify dependency and test discovery as parameterised low-pressure currents.
5. Synchronise child activation to validated parent inspection outputs.
6. Compile the resulting cyclone into CIR.
7. Execute in shadow mode against held-out repositories.
8. Compare correctness, latency, inference consumption and total cost.

This workload is preferable to starting with autonomous code modification because it exercises the core architecture while limiting irreversible side effects.

## 16. Explicit non-goals

The initial Cyclone release SHALL NOT attempt to:

- Replace general-purpose language models.
- Compile arbitrary semantic reasoning into deterministic code.
- Guarantee equivalence for unobservable external state.
- Automatically authorise actions based on historical repetition.
- Require native machine-code generation for every current.
- Optimise workflows at the expense of correctness or recoverability.
- Treat observed correlation as proof of causal dependency.
- Treat repeated agent mistakes as desirable behaviour.

These exclusions preserve a tractable engineering scope.

## 17. Required engineering deliverables

A release candidate SHALL include:

- Versioned architecture specification and ADRs.
- Rust workspace with independently testable subsystems.
- Formal CIR schema and validation rules.
- Trace ingestion and causal reconstruction implementation.
- Pressure classifier with explainable evidence.
- Current compiler and cyclone graph optimiser.
- Guarded execution runtime.
- Artifact registry and lifecycle manager.
- Security and tenancy enforcement.
- Replay, differential and adversarial test suites.
- Benchmark corpus and reproducibility manifests.
- Operational dashboard and telemetry exporters.
- Developer SDK and agent integration adapters.
- Deployment, incident response and rollback documentation.
- Measured performance and economics report.

## 18. Final engineering directive

Cyclone SHALL be built around three non-negotiable principles.

First: observation is evidence, not authority. Repetition may justify investigation and compilation, but never bypasses validation, permissions or semantic checks.

Second: pressure is a runtime property, not a permanent label. Currents must be able to mature, degrade, recover and retire as the evidence changes.

Third: optimise the cyclone, not only its currents. Individual computational efficiency is subordinate to correctness and total workflow efficiency.

The intended end state is an agent ecosystem in which recurring computational behaviour progressively becomes explicit, typed, verified and inexpensive execution infrastructure—while novel reasoning remains available precisely where it adds value.

Cyclone's defining capability is therefore not simply automation or caching. It is the continuous conversion of observed agent execution into governed, reusable computational machinery.

Directive status: Proposed architecture baseline. Implementation readiness requires Phase 0 repository inspection, interface validation, workload benchmarking and approval of security and equivalence policies.
